# Doubt Review

在决策仍易纠正时进行压力测试。这是 `decision-review` 协议的用户可调用伙伴，不替代运行时门禁或最终实现审查。

## 何时使用

- 用户明确要求怀疑审查、对抗性审查或怀疑性审查
- 决策改变分支逻辑、模块边界、共享状态、排序、幂等性
- 即将声称不熟悉或高风险代码的行为正确性
- L2 任务需要 `decision-review.jsonl` 证据

## 何时跳过

- 机械变更：格式化、文件移动、明显的一行编辑
- 仅阅读或总结现有代码
- 用户明确要求优先速度

## 五步怀疑循环

### 1. CLAIM

写清晰 2-3 行决策：

```text
CLAIM: "<一句话决策>"
WHY THIS MATTERS: <为何此决策错误代价高昂>
```

若无法简短陈述主张，继续研究直到决策具体化。

### 2. EXTRACT

创建最小可审查工件：

- 代码：聚焦的 diff、函数或测试用例，非整个文件
- 设计：3-5 句加必须成立的约束
- 移除作者推理；审查者应看到输入，而非结论

### 3. DOUBT

找问题，而非确认：

```text
找出此工件的问题。假设作者过度自信。寻找：
- 未声明的假设
- 未处理的边缘情况
- 隐藏耦合或共享状态
- 违反契约场景
- 破坏现有约定
- 意外输入下的失败模式

不要确认。不要总结。找问题，或明确声明审查后未找到问题。

ARTIFACT: <粘贴工件>
CONTRACT: <粘贴约束>
```

只传递 ARTIFACT + CONTRACT，不要传递 CLAIM。包含 CLAIM 会使审查者偏向同意。

子代理上下文中无法生成新鲜上下文审查者。若子代理内需要怀疑，返回主会话运行审查。

### 4. RECONCILE

按顺序分类每个发现：

1. 契约误解：修复契约，重新分类
2. 有效且可操作：修改工件，重启怀疑循环
3. 有效但已接受的权衡：显式记录权衡
4. 噪音：记录并排除

### 5. STOP

满足一个条件时停止：

- 下一轮仅产生琐碎的或已考虑的发现
- 三个循环完成；报告剩余实质性发现而非开始第四轮
- 用户说够了

三个循环后的实质性发现意味着工件太大或太不成熟。返回 EXTRACT 并拆分。

## 证据

为 L2 准备，在 `<task>/decision-review.jsonl` 中使用内部 `decision-review` 协议记录接受的决策。至少必须包含 `acceptanceId`、`claim`、`contract`、`reviewerContext`、`findings`、`resolution`。

## 常见合理化

| 借口 | 为何失败 | 更好方法 |
|---|---|---|
| "我有信心，跳过怀疑" | 信心是盲点藏身之处 | 写 2 行 CLAIM，传递工件给新鲜上下文审查 |
| "派生审查者很贵" | 实现后调试坏决策更贵 | 现在运行有界怀疑循环 |
| "审查稍后捕获" | 最终审查捕获完成的工件；怀疑在便宜时捕获方向错误 | 承诺方向前运行怀疑 |
| "怀疑每步都延迟" | 怀疑仅适用于非平凡决策 | 使用 何时使用/何时跳过 部分决定 |
| "审查者不同意，所以我错了" | 审查者输出是信息，非权威 | 通过 RECONCILE 分类每个发现 |

## 关系

- `decision-review`：内部强制 L2 门；写接受证据到 `decision-review.jsonl`
- `review-protocol`：最终实现审查；不替代飞行中怀疑
- `cowork-flow`：公共路由器；决定加载此技能还是内部协议
- `TDD`：当风险是可执行行为时，失败测试是具体的怀疑
- `break-loop`：当怀疑暴露真实失败模式但修复路径循环时使用
