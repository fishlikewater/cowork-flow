# Workflow Starter

> 一个用于新项目接入的通用协作 starter，组合了 `AGENTS.md`、`OpenSpec`、`superpowers` 与 `Trellis`。  
> 它提供的是“流程骨架”，不是“项目实现标准答案”。

---

## 1. 先理解这个 starter 是什么

这个 starter 解决的不是业务实现问题，而是协作方法问题：

- 如何先讨论需求，再开始编码
- 如何在有行为变化时先补规格
- 如何把计划、执行、review、留痕串成闭环
- 如何让 AI 在不同项目里保持一致的工作方式

它**不**负责替你的项目决定：

- 具体技术栈
- 具体目录结构
- 具体测试命令
- 具体发布方式
- 具体模块边界

所以在新项目中使用时，正确姿势不是“原样照搬”，而是：

1. 先保留流程层
2. 再替换项目事实层
3. 最后删掉不适用的部分

---

## 2. 核心原则

### 2.1 事实优先于模板

如果模板内容和目标项目现状冲突，以目标项目现状为准。

例如：

- 项目没有前端，就不要强保留前端 spec
- 项目没有 OpenSpec CLI，就不要硬套 `openspec` 命令
- 项目不允许 AI 提交代码，就统一改成“由人类提交”

### 2.2 流程要保留，内容要适配

通常应该保留的是：

- “先读规范再编码”
- “行为变更先补规格”
- “方案确认后再写计划”
- “执行后要验证、review、记录 session”

通常必须改写的是：

- 技术栈描述
- 命令示例
- spec 内容
- 提交方式
- 测试 / 构建 / 发布门禁

### 2.3 没有这个场景，就删掉

这个 starter 故意保留了前端、后端、跨层、OpenSpec 等通用入口。  
如果你的项目根本没有这类场景，最好的处理不是“保留占位”，而是**删除不适用部分**。

### 2.4 README 应该约束“判断方式”，而不是限制“实现方式”

好的 README 不应该把 AI 锁死成“必须按某个文件清单做机械替换”。  
它更应该告诉 AI：

- 先判断项目事实
- 再决定保留 / 改写 / 删除
- 最后验证流程是否闭环

## 3. 这个 starter 里有什么

```text
template/
├── AGENTS.md
├── .trellis/
├── .agents/skills/
├── openspec/
└── docs/superpowers/
```

各部分职责：

- `AGENTS.md`
  - 项目总规范、语言、提交口径、协作约束
- `.trellis/workflow.md`
  - 主流程定义
- `.trellis/spec/`
  - 项目开发规范
- `.trellis/scripts/`
  - 任务、上下文、journal 记录脚本
- `.agents/skills/`
  - `start / finish-work / record-session` 等本地技能入口
- `openspec/`
  - 行为变更的 proposal / spec / design / tasks / archive
- `docs/superpowers/`
  - 设计稿与开发计划输出目录

---

## 4. 文件怎么处理：不是“必改清单”，而是“判定矩阵”

下面这张表比“必须改 / 按需改”更适合 AI 落地。

| 路径 | 默认动作 | 什么时候保留 | 什么时候改写 | 什么时候删除 |
|------|----------|--------------|--------------|--------------|
| `AGENTS.md` | 必须核对 | 只保留协作原则 | 技术栈、语言、测试命令、提交口径都要改 | 几乎不删 |
| `.trellis/workflow.md` | 必须核对 | 保留流程骨架 | 命令、分级规则、门禁、提交方式要改 | 项目完全不用 Trellis 时才删 |
| `.trellis/spec/backend/` | 按事实适配 | 项目有后端 | 替换成真实后端规范 | 没后端就删 |
| `.trellis/spec/frontend/` | 按事实适配 | 项目有前端 | 替换成真实前端规范 | 没前端就删 |
| `.trellis/spec/guides/` | 通常保留 | 项目需要跨层 / 复用提醒 | 按项目风险点改写 | 极简项目可精简 |
| `.trellis/scripts/` | 通常保留 | 需要任务 / journal / context | 只改配置，不轻易改脚本 | 不用 Trellis 时删 |
| `.agents/skills/` | 默认保留 | 继续用这套协作流 | 原则上不按项目改；项目事实写入 `AGENTS.md`、`.trellis/workflow.md`、`.trellis/config.yaml` 和 `.trellis/spec/` | 不用本地技能系统时删 |
| `openspec/` | 按事实适配 | 项目能跑 OpenSpec，且需要行为变更治理 | 改 `config.yaml` 和说明 | 项目不用 OpenSpec 时删 |
| `docs/superpowers/` | 通常保留 | 需要 spec / plan 输出 | 一般只改说明，不改目录 | 不用 superpowers 时删 |
| `.trellis/workspace/` | 保留结构 | 只保留模板索引 | 不带历史 journal | 不删 |
| `.trellis/tasks/` | 保留空结构 | 需要任务目录 | 不带旧任务实例 | 不删 |

## 5. AI 在新项目中落地时应遵循的规则

如果你让 AI 根据本 README 把 starter 接入到另一个项目，建议它遵循以下规则：

### 5.1 先看项目，再改模板

AI 第一轮应该先做：

1. 识别项目语言和主要技术栈
2. 识别项目是前端、后端、monorepo 还是混合仓库
3. 识别现有测试、构建、提交、发布方式
4. 识别项目是否已经有自己的规范系统

不应该一上来就机械复制模板内容。

### 5.2 先决定接入层级

接入通常有 3 个层级：

#### A. 完整接入

适合：

- 新项目
- 想同时启用 `AGENTS + Trellis + OpenSpec + superpowers`

#### B. 部分接入

适合：

- 老项目
- 只想接入 `AGENTS + Trellis`
- 或只想接入 `AGENTS + OpenSpec`

#### C. 仅方法接入

适合：

- 项目已有自己的脚手架和规范系统
- 只想吸收这里的流程思想，不直接复制目录

AI 应先判断属于哪一类，再决定动作。

### 5.3 先删不适用部分，再补适用部分

不要让模板在新项目里留下大量“未来可能会用”的空壳。  
这会制造噪音，也会误导后续 AI。

优先顺序应该是：

1. 删除不适用模块
2. 改写保留模块
3. 再补充项目特有规则

### 5.4 不保留旧项目痕迹

AI 落地后，应再次扫描并清理：

- 旧项目名
- 旧技术栈
- 旧命令
- 旧路径
- 旧模块名
- 旧提交规则

如果还有旧痕迹，说明接入没有完成。

### 5.5 Skill 保持模板级泛化，不在项目接入时改写

`SKILL.md` 的职责是描述可复用的触发条件、执行步骤、检查点和决策规则。  
它不应该退化成某个项目、某个阶段、某个一次性任务的施工清单。

接入具体项目时，**默认不要修改 `.agents/skills/**/SKILL.md`**。项目差异应落在这些位置：

- `AGENTS.md`：技术栈、测试命令、提交策略、语言口径
- `.trellis/workflow.md`：流程分级、门禁、完成定义
- `.trellis/config.yaml`：可配置命令、hook、记录策略
- `.trellis/spec/`：项目真实代码规范、目录规范、契约规范

应优先写：

- 场景类型，例如“数据库初始化文件”“接口契约文件”“迁移脚本目录”
- 判定规则，例如“当修改数据库 schema 时，需要核对初始化脚本、迁移脚本和查询实现是否同步”
- 如何读取项目事实，例如“先查看 `AGENTS.md` 和 `.trellis/config.yaml` 中的验证命令”

应避免写：

- 某个业务仓库独有的模块名
- 某个一次性任务才成立的复选项
- 没有抽象价值的具体文件路径
- 要求落地时替换的裸占位命令，例如 `<test-command>`、`<lint-command>`

只有当某个 skill 明确就是“当前项目专用 skill”时，才可以带入项目专有上下文；并且应在名称、描述或文档开头明确说明其专用性。

### 5.6 如确需修改 Skill，保持原文件语言一致

只有在用户明确要求创建或修改项目专用 skill 时，才修改已有 skill；修改时不要把语言风格改成中英混写。

- 原文件是中文，新增内容继续使用中文
- 原文件是英文，新增内容继续使用英文
- 如果确需整体切换语言，应整体改写，而不是局部插入另一种语言

### 5.7 开发计划是活文档，执行中必须同步状态

`superpowers:writing-plans` 产出的 `docs/superpowers/plans/*.md` 不应被当作“一次性写完就不再维护”的附件。  
只要计划进入执行阶段，它就应被视为当前任务的活文档之一。

至少应满足：

- 任务和步骤使用 checkbox 语法，便于直接回写完成状态
- 计划中存在 `当前执行状态` 一类的区块，用于记录日期、批次、阻塞、验证或 review 结果
- 已完成且验证通过的步骤，应及时从 `- [ ]` 改成 `- [x]`
- 尚未完成或被阻塞的步骤，不应误勾选；应保留未完成状态并补充原因

执行完成前，还应核对：

- 计划勾选状态与真实实现进度一致
- 计划中的最新验证 / review 结论与实际证据一致
- 计划状态与 Trellis / OpenSpec 的高层状态不冲突

## 6. 推荐迁移流程

### 步骤 1：复制模板

把 `template/` 下内容复制到新项目根目录。

### 步骤 2：做“项目事实替换”

至少要替换：

- `AGENTS.md` 中的技术栈、命令、提交口径
- `.trellis/workflow.md` 中的验证命令、流程分流、门禁
- `.trellis/spec/` 中的技术与架构描述
- `openspec/config.yaml` 中的项目上下文

### 步骤 3：删除不适用部分

例如：

- 没前端，就删 `.trellis/spec/frontend/`
- 没 OpenSpec，就删 `openspec/` 并同步删 workflow 中相关要求
- 不允许 AI 提交，就统一改 `AGENTS.md` 和 workflow 里的提交口径；不要为此改 reusable skill

### 步骤 4：验证脚本入口

至少确认：

```bash
python3 ./.trellis/scripts/get_context.py
python3 ./.trellis/scripts/init_developer.py demo-user
```

如项目保留 OpenSpec，再确认：

```bash
openspec validate --strict --help
```

### 步骤 5：让 AI 用一次真实任务跑通

不要只看文件是否存在。  
应当用一个真实小任务验证：

- AI 是否能正确识别 `L0 / L1 / L2`
- 是否会先读规范
- 是否会在行为变更时先补 OpenSpec
- 是否会在实现后走验证、review、record-session

## 7. 按场景接入

### 场景 A：只有后端项目

建议：

- 保留 `backend/`
- 精简或删除 `frontend/`
- 保留 `guides/`
- 保留 `OpenSpec + Trellis`

不要做的事：

- 留下一整套前端规范占位但项目里根本没有前端

### 场景 B：只有前端项目

建议：

- 保留 `frontend/`
- 精简 `backend/`
- 如果后端契约来自远程 API，可在 `guides/` 中保留契约同步规则

### 场景 C：前后端分离仓库

建议：

- 在 `spec/` 中分别写前后端索引
- 在 `guides/` 中重点强化跨层契约与接口变更传播

### 场景 D：Monorepo

建议：

- 保留这套流程骨架
- 把 spec 改成“按 workspace / package / app / service”组织
- 明确不同子项目共用哪些规范、各自覆盖哪些规范

### 场景 E：已有成熟工程规范的老项目

建议：

- 不要整套硬插
- 优先接入 `AGENTS.md`
- 再按需要接入 `OpenSpec` 或 `Trellis`
- 已有系统与 starter 冲突时，以项目现有稳定规则为准

### 场景 F：没有 OpenSpec CLI

有两种做法：

1. 安装 OpenSpec，再保留完整流程
2. 暂时删掉 `openspec/`，但保留“行为变更先写 proposal / spec / plan”的思想，用项目自己的文档目录承接

不要既没有 OpenSpec，又在 workflow 里保留大量 `openspec` 命令。

## 8. 推荐给 AI 的接入任务定义

如果你要让 AI 把这个 starter 接入到别的项目，推荐这样描述，而不是只说“按 README 落地”：

```text
请将 /opt/projects/workflow-starter/template 接入当前项目。

要求：
1. 先分析当前项目事实，再决定保留、改写或删除哪些模板内容。
2. 保留流程骨架，不机械保留与项目不符的占位内容。
3. 以项目真实技术栈、测试命令、提交流程为准，改写 AGENTS.md、.trellis/workflow.md、.trellis/config.yaml、.trellis/spec/、openspec/config.yaml。
4. 不要修改 `.agents/skills/**/SKILL.md`；除非用户明确要求创建项目专用 skill。
5. 如果某个子系统在当前项目不存在，直接删除对应模板内容，不要保留空壳。
6. 完成后给出“哪些内容保留、哪些改写、哪些删除、为什么”的摘要。
7. 最后用实际命令验证关键入口可运行。
8. 如果接入后要使用 `superpowers` 开发计划，必须把 `docs/superpowers/plans/*.md` 视为执行期活文档，在执行中持续回写勾选状态与当前执行状态。
```

这样 AI 的行为会更稳定，也更不容易被 README 的表面结构绑死。

## 9. 常见错误

### 错误 1：把模板当成项目事实

表现：

- README 写什么就原样搬什么
- 技术栈、命令、目录结构全都不核对

正确做法：

- 先看项目事实，再适配模板

### 错误 2：只复制，不删减

表现：

- 项目没有前端，却保留大量前端规范
- 项目没有 OpenSpec，却保留所有 `openspec` 命令

正确做法：

- 无此场景就删

### 错误 3：只改文档，不跑入口

表现：

- 文档看起来正确，但脚本、命令、流程根本跑不通

正确做法：

- 至少验证初始化、上下文获取、任务创建、必要时 OpenSpec 命令

### 错误 4：README 写得太像施工单

表现：

- AI 把 README 理解成固定脚本
- 后续实现空间被锁死

正确做法：

- README 写原则、判定和验收
- 具体实现细节留给项目 spec 和计划文档

### 错误 5：把 skill 改成项目临时清单

表现：

- skill 里出现当前项目独有的模块名、文件名、任务复选框
- 接入项目时为了替换测试命令、提交策略而修改 reusable skill
- 过几周再看，除了当次任务几乎没有复用价值

正确做法：

- 把具体项目对象抽象成场景类型、目录类型和判定规则
- 项目事实写入 `AGENTS.md`、`.trellis/workflow.md`、`.trellis/config.yaml` 或 `.trellis/spec/`
- 只有“明确专用”的 skill 才允许保留项目特有内容

### 错误 6：在已有 skill 中中英混写

表现：

- 英文 skill 中插入中文段落
- 中文 skill 中插入英文规则

正确做法：

- 跟随原文件语言追加内容
- 如需换语言，整体统一改写

### 错误 7：计划写完后不再回写状态

表现：

- `superpowers:writing-plans` 已生成计划，但执行过程中从不更新 checkbox
- 代码已经完成，计划文档仍显示大量未完成步骤
- `Trellis` / `OpenSpec` / 计划文档三者状态彼此不一致

正确做法：

- 把计划文档视为执行期活文档
- 每个步骤在“完成且验证通过”后立即勾选
- 每轮 review、阻塞、收尾验收后都同步更新 `当前执行状态`

## 10. 怎样算真正接好了

不是“文件复制完了”就算接好，而是下面这些结果成立：

### 流程层

- AI 能正确区分 `L0 / L1 / L2`
- 行为变更时会先补规格、再写计划、再执行
- 执行后会走验证、review、record-session

### 项目事实层

- `AGENTS.md` 和 `.trellis/spec/` 已反映真实项目技术栈
- README、workflow、配置与 spec 中的命令是真实可执行的；skills 只负责读取这些项目事实
- 不存在旧项目名和旧模块名残留

### 协作层

- 提交口径一致
- 是否允许 AI 提交业务代码已经统一
- `.trellis` 元数据如何提交已经统一

### 验证层

- 关键脚本可运行
- 至少用一个真实任务试跑过一次
- 若项目使用 `docs/superpowers/plans/`，计划中的勾选状态、当前执行状态与真实进度保持一致

如果这些条件都满足，才说明 starter 不是“复制过去了”，而是“真正接好了”。

## 11. 当前目录说明

你当前看到的是：

- `README.md`：迁移说明
- `template/`：真正要复制到新项目的模板目录

如果你希望把这个 starter 继续发展成更强的版本，可以再加：

- `examples/`：不同项目形态的示例
- `prompts/`：给 AI 的标准接入提示词
- `checks/`：迁移完成后的自动检查脚本

但这些都属于增强项，不是 starter 的必需项。
