# Workflow Optimization Roadmap Proposal

## 背景

当前 cowork-flow 已从模板仓库演进为“轻量协作运行时 + 模板分发工具”：

- NPM CLI 负责安装、同步、更新和发布边界。
- `.cowork-flow/scripts/` 负责 Python runtime、任务生命周期、DB 状态、质量门禁、dashboard 和子代理运行时。
- `template/` 是对外分发面，需要与根目录实现保持严格同步。
- `.agents/skills`、`.codex/agents`、`.claude/skills`、`.opencode/plugins` 承担不同宿主的人机与固定代理契约。

上一轮分析暴露的主要问题不是缺少单点功能，而是维护复杂度上升：状态权威边界需要继续收敛，root/template 容易漂移，核心 Python 文件过大，宿主契约需要更强回归测试，新用户闭环和维护者诊断体验仍可提升。

## 目标

在不重写安全内核、不引入第二套状态机的前提下，分阶段降低 cowork-flow 的维护成本和回归风险，形成可执行、可验收、可归档的优化路线图。

## 用户价值

- 维护者可以在已有安全内核不被重写的前提下，按可验收任务逐步降低运行时维护成本。
- 使用者可以获得更稳定的模板同步、发布健康检查、正式子代理契约和新用户闭环体验。
- 后续重构会被状态权威矩阵、sync gate 和宿主契约测试保护，减少回归风险。

## 非目标

- 不重新设计 runtime-context binding 或 fail-closed 安全模型。
- 不改变固定 `cowork-*` 代理的叶子执行者边界。
- 不把 Party Mode 重新移回主 workflow。
- 不在一个任务里同时做 DB schema 迁移、CLI 重构、宿主契约和文档重写。
- 不覆盖当前未提交代码改动；每个任务执行前必须重新确认 diff 边界。

## 关键假设

- 当前安全内核继续以 DB untime_context / untime_session 为权威，不引入第二套执行状态。
- root/template 同步是发布质量的关键风险，应先建立门禁再做大文件拆分。
- P2 结构拆分必须行为保持，默认不改变 CLI 参数、退出码和公开状态机语义。
- 当前工作区已有未提交改动，每个任务执行前必须重新确认 diff 边界。

## 范围

本 change 覆盖 8 个任务：

1. P0 规划基线与风险盘点。
2. P1 强化 doctor 与发布前健康检查。
3. P1 建立 root/template 同步强门禁。
4. P1 收敛运行时状态权威。
5. P2 拆分任务生命周期运行时服务层。
6. P2 拆分 FlowStore 存储与迁移边界。
7. P2 强化正式子代理宿主契约测试。
8. P3 文档与新用户闭环体验重构。

## 验收标准

- 每个任务都有独立 PRD、上下文、验证命令和明确非目标。
- 总计划说明串行/并行策略、依赖关系、风险和集成验证。
- P0 先产出状态权威矩阵、文件复杂度基线、测试覆盖基线和 root/template 差异基线。
- P1 先做低风险高收益的诊断与同步门禁。
- P2 的结构拆分必须行为保持，并用现有测试或新增回归测试证明。
- P3 文档重构必须围绕真实最小闭环，不引入与 runtime 不一致的流程说法。
